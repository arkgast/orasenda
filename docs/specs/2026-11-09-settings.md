## TL;DR
- P1 sub-project **B**: a **Settings page** that holds what Today will stop showing. Sections **General** (theme), **Timer** (default preset, Custom focus and break minutes), **Notifications** (one checkbox), **Apps and sites** (one interim line) and **About and data** (version, platform, privacy, licence). It saves on change, has no Save button and no primary, and says what failed beside the field and in its save line.
- **Notifications are off by default.** Nothing asks macOS for permission until the user ticks *Tell me when a session ends*. `timer_start` stops asking, Today loses its "Orasenda can tell you…" line, and existing installs get a one-time **notify review**: the preference stays on only if macOS already granted it.
- **Theme** *Match system / Light / Dark* is saved as `ui.theme`, applied in Rust to the whole app (`AppHandle::set_theme`, so the title bar and the menu-bar menu follow) and in the webview with `data-theme` on `<html>`.
- Reachable from the rail, **⌘,** (a new *Settings…* item in the app menu) and *Settings…* in the menu-bar menu. Regular layout only: the window minimum stays 900×600 and the compact layout is C's.
- One decision gets an ADR: **ADR-014**, settings as one object saved through one chain, with side effects applied in Rust and a `settings-changed` event. Later specs that add settings (E, F, G, P5/P6) follow it.
- **Size: one design-system task, then five code tasks.** The seven components B builds on (`PageFrame`, `ScrollRegion`, `SettingsIndex`, `SettingsRow`, `InlineNotice variant="row"`, `Input unit`, `EmptyState variant="inline"`) are specified in the design-system PR but not built in its `bundle.js`. Building them design-first (artifact, then `design/system/`, then `packages/ui`) is a task of its own, with its own both-themes and keyboard checks, and the plan lists it first (see [Decisions](#decisions)).
- Section names follow the re-cut ruling and the design-system READMEs (**General**, **Timer**, **About and data**), not the canvas the owner approved (*Appearance*, *Focus times*). Said here once so the difference is a known one.

## Change in a nutshell
After `pnpm --filter orasenda tauri dev`, press ⌘, (or click *Settings* in the rail):

```
│ ▢ │  Settings                                                             │
│ ▢ │  Changes save as you make them.                                       │
│ ▢ │ ┌────────────────────┐  General                                     ┃│
│ ▢ │ │▌General            │  Theme                                       ┃│
│ ▢ │ │ Match system       │  (•) Match system  ( ) Light  ( ) Dark       ┃│
│ ▣ │ │ Timer              │  Match system follows macOS. Light and Dark  ┃│
│   │ │ Classic 25/5       │  also set the title bar and the menu-bar menu.│
│   │ │ Notifications      │ ───────────────────────────────────────────── │
│   │ │ Off                │  Timer                                        │
│   │ │ Apps and sites     │  Preset                                       │
│   │ │ Nothing recorded   │  (•) Classic 25/5  ( ) 50/10                  │
│   │ │ About and data     │  ( ) Deep Block 90  ( ) Custom 45/10          │
│   │ │ Version 0.1.0      │  ⌄ More below                                 │
```

Type 3 in *Focus minutes* and press Return: the field keeps "3", its border thickens, and beside it the alert glyph and "Between 5 and 180 minutes. Still using 45." appear. The save line reads "Focus minutes weren't saved. Still using 45." with *Show*. Tick *Tell me when a session ends* on a fresh install: the macOS prompt appears now, and only now. *Allow* leaves the box ticked with "On. A notification appears when a session ends while Orasenda is in the background." *Don't Allow* turns the box back off and shows "macOS has notifications off for Orasenda." with *Open System Settings*. Choose *Dark*: the page, the title bar and the menu-bar menu turn dark at once and stay dark after a relaunch.

Today changes in one way: the "Orasenda can tell you when a session ends…" line is gone, and *Start focus* never brings up a permission prompt.

Behind it: one `Settings` object (`theme`, `preset`, `custom`, `notifySessionEnd`) goes through `settings_get` / `settings_set` and the existing save chain (`apps/orasenda/src/settingsQueue.ts`). Rust applies the theme after a save and emits `settings-changed`. Migration `0002` marks pre-B databases for the notify review, which the app crate runs once the launch read of the notification status arrives. A new `notifications_request` command is the only caller of `Notifier::request`.

## Problem
Configuration lives on Today today: the preset radios and the two Custom fields sit between the ring and the Start button (`apps/orasenda/src/pages/Today.tsx:220-270`). The owner's Today asks (minimal, configuration off Today, a 360×240 minimum) need somewhere else to put it first, and the C spec (the Today redesign) can't remove anything until that place exists. Separately, Orasenda asks for the notification permission the first time a session starts (`apps/orasenda/src-tauri/src/session.rs:505-507`, `scheduler.rs:175-177`), so the very first *Start focus* also brings up a system prompt. That puts a decision in front of the lowest-cost action in the app. The owner decided notifications are off by default and requested only when the user turns them on. There is no theme choice: the app always follows the system (`packages/tokens/build.ts:121` emits only a `prefers-color-scheme` block). A failed settings save rolls back with no word of why (`settingsQueue.ts:157-164` logs and rolls back; #112 closed the Rust half only).

## Goals / Success criteria
1. *Settings* in the rail, ⌘, from any page, and *Settings…* in the menu-bar menu each show the main window on the Settings page with focus on its `h1`, also when pressed before the webview listens (cold start). The page renders five sections from `PageFrame`, `SettingsIndex`, `SettingsRow`, `ScrollRegion` and the save line (`InlineNotice variant="row"`).
2. Theme: choosing *Light* or *Dark* changes the webview, the title bar and the menu-bar menu within one second and survives a relaunch. *Match system* removes both overrides. On a fresh install the value is *Match system*.
3. Timer: the default preset and Custom minutes save on change (fields on blur or Return, Esc restores the saved value). Both helpers are always visible, and both fields show whichever preset is chosen. An out-of-range or non-numeric value is refused beside the field and in the save line, and the typed value is kept (#120, Settings half).
4. A `write` or `unavailable` failure from `settings_set` rolls the control back and shows the #112 copy: the reason beside the setting, and the setting with its restored value plus *Try again* in the save line. No failure is silent.
5. Notifications: a fresh install never shows a permission prompt unless the user ticks the checkbox. `timer_start` makes no `Notifier::request` call in any status. The Notifications row's eight rows (seven states: off, not asked yet, asking, on, denied, denied but wanted, unavailable; `granted`+off and `notDetermined`+off are both Off with different lines) each show their line, and the status is re-read when the main window gains focus.
6. Existing installs: after the first B launch, `notify.session_end` is `true` only if it was `true` (or never written) **and** macOS reported `granted`. The review runs once per database.
7. The UI uses only design-system tokens and components. Both themes render. VoiceOver reads the index, the save line once per change, the checkbox's busy state and each field's error. The page works by keyboard alone.
8. In the real engine (WKWebView, real fonts) at 900×600 and 1440×900, in both themes, no content is hidden. The page itself never scrolls (`document.scrollingElement.scrollHeight <= innerHeight`), only the `ScrollRegion` does, the header and save line stay in place, and the longest lines wrap inside their rows (see [Testing](#testing-strategy)).
9. ADR-014 is accepted by the last task. `CONTEXT.md` defines the new terms. Spec A carries the amendments listed below.

## Non-goals
- Any Today layout change other than deleting the explanation line: the preset radios and Custom fields stay on Today until C removes them. The window minimum, the compact Settings layout (*Jump to section* menu, Pages menu) and the layout harness are C's.
- Settings › Keyboard, global shortcuts and *Single-key shortcuts* (F). *Reading comfort font (Lexend)* and *Show "Just 2 minutes"* (separate backlog items). E's Timer rows (long break, rounds, extension cap) and *Two minutes before the end* (E).
- About and data's data rows: session count, data folder and *Show in Finder*, export, import, backups and *Delete all data* (G). Apps and sites content (P5/P6). ⌘K (D). In-app ⌘1–6 and ⌘[ (C).
- A third-party licence list. About shows Orasenda's own licence only (see [Open questions](#open-questions)).
- The app menu's *About Orasenda* keeps the native panel. Sending it to Settings › About (a canvas call) waits until G adds the data rows.
- Notification sound or content changes. The end notification is spec A's, unchanged.
- Re-asking macOS after a denial. macOS doesn't show the prompt twice, and System Settings is the way back.

## Users & permissions
One local user, no accounts.

| Caller | Can | Cannot |
|---|---|---|

| Orasenda process | Spec A's rights; set the app appearance (`NSApplication.appearance` through `AppHandle::set_theme`); open one `x-apple.systempreferences:` URL through `NSWorkspace` | Any URL other than the Notifications pane; any TCC permission other than Notifications |

- The three commands go into `apps/orasenda/src-tauri/commands.list.rs`, `specta_builder()` (`apps/orasenda/src-tauri/src/lib.rs:20-46`) and `capabilities/main.json` (`allow-notifications-request`, `allow-notifications-open-settings`, `allow-navigate-take`), like every command (conventions, "Code structure").
- **Permission at the moment of need, and only then.** `Notifier::request` has exactly one caller, `notifications_request`, and the only control that calls that command is the Notifications checkbox (or its *Ask macOS* action, see [Behavior](#behavior--edge-cases)). This is the SPEC's "permissions at the moment they're needed" (SPEC line 153) and design-system README rule 29.

## Tenancy & localization
- Single user, single device. `ui.theme` and `notify.session_end` are syncable settings (`setting` rows with `change_log`, ADR-012), like spec A's keys. The notification *status* is per device and is never stored: it is read from macOS. The notify review marker is device-only (`meta`).
- Copy is English only. The version line uses `app_info` (`apps/orasenda/src/format.ts:3-20` already maps `os` to "macOS"). No time strings are new; nothing here formats time.

## Domain model
Terms are defined in [CONTEXT.md](../../CONTEXT.md): **notification status** (what macOS allows: `notDetermined | granted | denied | unavailable`, core `NotificationStatus`, `crates/core/src/platform.rs:73-78`) and **notification preference** (`notify.session_end`, what the user wants) are separate. A notification is posted only when both say yes. Also **save line**, **notify review** and **theme override**.

### Settings (app crate, ADR-014)
| Key | Type | Default | Notes |
|---|---|---|---|
| `ui.theme` | `Theme = system \| light \| dark` (serde lowercase) | `system` | New. An undecodable value is logged and read as `system`, like spec A's keys (`session.rs:714-726`). |
| `timer.preset` | `Preset` | `classic` | Unchanged (spec A). |
| `timer.custom` | `CustomSpec` | 45/10 | Unchanged. Valid when `5 ≤ focus ≤ 180` and `1 ≤ break ≤ 60` (`CustomSpec::validate`). |
| `notify.session_end` | bool | **`false`** (was `true`, `ipc.rs:132`) | While a notify review is pending, an absent key reads as `true` (spec A's default) so the review sees what A meant. |

- The IPC type `TimerSettings` (`ipc.rs:118-135`) becomes **`Settings { theme, preset, custom, notifySessionEnd }`**, still `deny_unknown_fields`. `settings_get() -> Settings` and `settings_set(settings: Settings)` keep their shape otherwise. The rename is mechanical: `bindings.ts` is regenerated, and `settingsQueue.ts`'s `SETTINGS_KEYS` gains `"theme"` (its compile-time check fails until it does, `settingsQueue.ts:36-46`).
- `set_settings` validates as today (`quick` and an out-of-range `custom` are `invalidSpec`). It then **writes only the keys whose value differs from the presented settings** (below), in one transaction with anything owed. Today it upserts all three keys on every save (`session.rs:436-439`), and `settings::set` logs one `change_log` row per call (`crates/store/src/settings.rs:22-30`), so a one-field change logs every key. A save that changes nothing writes no setting row (it still writes anything owed, as today) and succeeds. The diff is computed under the session lock against the presented settings (derived from the cache; below), so it also tells which side effects to run: `theme` in the diff is what gates `set_theme`.
- **Presented settings.** What `settings_get`, `settings-changed` and the diff use. Equal to the cache, except while a notify review is pending: then `notifySessionEnd` is presented as the review's outcome under the status known now, `(stored value, or true when absent) && status == granted`, and as `false` while the status isn't known yet. So the webview never sees the A-era `true` that the review might turn off, and a save that echoes the presented value back doesn't touch the key.
- **Marker and saves.** The review marker is removed only when a save's `notifySessionEnd` differs from the presented value, which only a user's tick or untick does. That save writes `notify.session_end` and `meta::remove("notify_review")` in one transaction (the user's choice wins over the review). A theme, preset or minutes save leaves the marker and the stored `notify.session_end` alone.
- `Theme` lives in the app crate (`ipc.rs`): it is a presentation preference, not product logic, so core doesn't need it.

### Notify review (one-time migration of existing installs)
- `crates/store/migrations/0002_notify_review.sql` sets `user_version = 2` (through the runner) and runs one statement: `INSERT INTO meta (key, value) SELECT 'notify_review', 'pending' WHERE EXISTS (SELECT 1 FROM meta WHERE key = 'device_id');`. On a fresh file, migrations run before `init_meta` writes `device_id` (`crates/store/src/lib.rs:155-157`), so no marker is written. On an A file the marker is written. `SCHEMA_VERSION` becomes 2 (`lib.rs:30`).
- New store module `meta.rs` (device-only, no `change_log`): `get(txn, key) -> Option<String>` and `remove(txn, key)`.
- The app crate's `SessionService` reads the marker with the settings, in the same read transaction (`read_settings`, `session.rs:695-712`, at launch and in `retry_recovery`, `session.rs:241-283`). The review needs two things: the settings and marker read, and a known status that is `granted`, `denied` or `notDetermined`. It runs, under the session lock, at the first moment both are true, which is one of three places, all calling one `SessionService::run_notify_review(now_ms) -> bool`: after `store_status` stores a status (the launch read, `scheduler::read_launch_status`, `scheduler.rs:283-286`, and also the focus re-read and a request's answer), and after `retry_recovery` reads the settings when the launch read had failed. The review writes `notify.session_end = (stored value, or true when absent) && status == granted` together with `meta::remove("notify_review")` in one transaction. Then, after unlock, one `settings-changed` goes out. `run_notify_review` is a no-op once the marker is gone, so calling it from each path is safe.
- The launch status read runs on every launch, on its own thread, whether or not the store opened (`session.rs:762`). If the store was unavailable, the status is stored while the marker is still unknown, and the review then runs from `retry_recovery` when the settings read recovers. If the store never opens in that run, the review waits for the next launch.
- `unavailable` (an unbundled `tauri dev` run, where `NoopNotifier` can't tell; `platform.rs` picks it outside a bundle) leaves the marker pending. A dev run never turns off a preference that the bundled app, which uses the same `app_data_dir()`, would keep.
- A failed write keeps the reviewed value in the cache and the marker on disk. The next launch reviews again by the same rule.

### Notifier trait (core) and `MacNotifier`
- `platform::Notifier` gains `fn open_settings(&self) -> Result<(), PlatformError>`. `NoopNotifier` returns `Unsupported`.
- `MacNotifier::open_settings` opens `x-apple.systempreferences:com.apple.Notifications-Settings.extension?id=<bundle id>` (the bundle id from `NSBundle.mainBundle.bundleIdentifier`) with `NSWorkspace.sharedWorkspace.openURL`, on the main thread through `run_on_main_thread`, and checks the returned `BOOL` (conventions, "Failures are never silent success"). The `NSWorkspace` feature is already enabled (`crates/platform-macos/Cargo.toml`). A pure `notification_settings_url(bundle_id) -> String` is unit-tested.

**Commands** (`#[tauri::command] #[specta::specta]`, camelCase, errors `{ kind, message }`):
- `settings_get() -> Settings`. Unchanged apart from the type. Defaults while the store is degraded.
- `settings_set(settings: Settings) -> Result<(), SettingsError>`. Unchanged contract (`invalidSpec | unavailable | write`, `ipc.rs:170-184`). On success, in this order after unlock: apply the theme if it changed, publish one `clock-tick` (as today, `session.rs:828-833`), emit `settings-changed`. A save that changes `view.store` still publishes one `timer-tick` first (#112, `session.rs:804-807`).
- `notifications_request() -> NotificationStatus`. An `async` command; never errors. It takes the known status, reading it off-lock if the launch read hasn't arrived. In any status other than `notDetermined` it returns that status without asking. When the status is `notDetermined` it asks **once per prompt**: `notifications.rs` keeps a `Mutex<Option<Vec<Sender<NotificationStatus>>>>` of waiters. The first caller finds `None`, puts in a list with its own sender and calls `Notifier::request`. A caller that finds a list already there adds its sender and never calls `Notifier::request`. The completion callback takes the list, stores the answer (one `timer-tick` when the shown status changed, as `store_status` does today, `scheduler.rs:227-232`, then the notify review if it is pending) and sends the answer to every waiter. Each waiter is a `tauri::async_runtime::channel(1)` (tokio's mpsc, re-exported by the pinned tauri, `tauri-2.12.5/src/async_runtime.rs:13-20`, so no new dependency); the callback uses `try_send`, and the command `await`s its receiver. **No thread is parked** while the prompt is up, and there is no timeout: a prompt left open costs one pending future. If the app quits, the process ends with it. A dismissed prompt is answered by macOS like *Don't Allow*. The command never writes a setting: the webview saves the preference through the chain. This replaces relying on how `requestAuthorizationWithOptions:` treats two overlapping calls, which Apple doesn't document.
- `notifications_open_settings() -> Result<(), NotificationsError>`. `kind: unavailable` (no bundle, `NoopNotifier`) or `failed` (`openURL` returned NO).
- `timer_start` **no longer requests**. `Outcome.request_notifications` and `Effects.request_notifications` (`session.rs:70-71`, `648-649`), the `matches!` in `start` (`session.rs:505-508`) and the call in `publish` (`scheduler.rs:175-177`) are removed. `request_permission` (`scheduler.rs:204-224`) moves to `notifications.rs` as the command's body.

**Events:**
- `settings-changed` with `Settings`. Emitted after a successful `settings_set`, after the notify review writes, and after a recovered launch read of the settings (`retry_recovery`, `session.rs:272-275`, which today updates the cache with no event, so a page that loaded defaults kept them). Never emitted under the session lock.
- `navigate` with `Navigate { page: NavigatePage }` (`today | board | calendar | routines | review | settings`, the `NavPage` values of `packages/ui/components.d.ts:50`). Emitted to `main` by `lifecycle::show_settings` after `show_main` (`lifecycle.rs:56-70`). In B only `settings` is sent. The event alone can be lost when the webview isn't listening yet, so Rust also keeps the request (next paragraph).

**Pending navigation.** `lifecycle::show_settings` first stores `Some(Settings)` in a managed `PendingNavigate(Mutex<Option<NavigatePage>>)`, then calls `show_main`, then emits `navigate`. A new command `navigate_take() -> Option<NavigatePage>` returns the stored page and clears it. The webview calls it once after its `navigate` listener is registered (when the shell's `subscribe()` resolves) and again on each `navigate` event, and goes to the page it returns. A page delivered twice (event and take) navigates once, since going to the current page does nothing. So a ⌘, or *Settings…* pressed before the webview listens, at a cold start, still lands on Settings. Closing `main` hides it and keeps the webview (`lifecycle.rs:36-46`), so a closed window has no other gap. `navigate_take` goes into `commands.list.rs`, `specta_builder()` and `capabilities/main.json` (`allow-navigate-take`).
- `timer-tick` is unchanged. It already carries `notifications` and `store`, which Settings reads through `useTimer`.

**Status re-read on focus.** `WindowEvent::Focused(true)` on `main` (`lifecycle.rs:35`) also starts one `notification-status` thread that calls `Notifier::status` and `store_status`. A single-flight `AtomicBool` in `notifications.rs` skips the read while one is in flight, so two quick focus events can't race two answers. A permission changed in System Settings shows when the user comes back, with no relaunch. `store_status` runs the pending notify review after storing, so a status that becomes known on focus also completes it.

**Theme.** After a save that changed `theme`, and in `setup()` once the service has read the settings, the app crate calls `AppHandle::set_theme(None | Some(Light) | Some(Dark))` (`tauri-2.12.5/src/app.rs:941`). On macOS this sets `NSApplication.appearance` for the whole app (`tao-0.37.2/src/platform_impl/macos/window.rs:369-387`), so every window's title bar, the menu-bar menu, and WKWebView's `prefers-color-scheme` follow. The call goes through the runtime to the main thread and is never made under the session lock (conventions). The `Host` trait gains `apply_theme(Theme)` so tests can record it. In the webview, `useTheme` (in `App`) calls `settings_get` once at mount and then follows `settings-changed`. An event that arrives before the get's answer wins, and the answer is then dropped. **No flash at launch (window show order).** Config windows are created before `setup` runs (`tauri-2.12.5/src/app.rs:2692` then `2698`), so a visible `main` could paint in the system appearance before `set_theme`. **`settingsQueue.ts`.** The chain is unchanged (conventions, "Newest wins"). ## Behavior & edge cases
- **Notifications row, by status and preference** (index value in brackets):

| Status | Preference | Box | Line | Action |
|---|---|---|---|---|
| `notDetermined` | off | off | "Turning this on asks macOS for permission, once." [Off] | none |
| `notDetermined` | on (synced or after `tccutil reset`) | on | "On here, but macOS hasn't been asked yet." [Not asked yet] | quiet *Ask macOS* → `notifications_request` |
| (asking) | — | on, `aria-busy` | "Waiting for your answer in the macOS prompt." [Asking macOS] | none |
| `granted` | on | on | "On. A notification appears when a session ends while Orasenda is in the background." [On] | none |
| `granted` | off | off | none [Off] | none |
| `denied` | off | off | "macOS has notifications off for Orasenda." [Off in macOS] | quiet *Open System Settings* (name "Open System Settings, Notifications for Orasenda") |
| `denied` | on | on | "On here, but macOS has notifications off for Orasenda. Allow them in System Settings and Orasenda will use them." [Off in macOS] | *Open System Settings* |
| `unavailable` | either | shows the preference, disabled | "Notifications aren't available in this build." [Not available] | none |

  The approved canvas and its review cover six of these rows. `notDetermined`+on (reachable after `tccutil reset`, and later through sync) and the bracketed index values other than *On* and *Off* are new. Under design-first they go into the artifact before code, in the design-system task: the eight rows (seven states) in the `SettingsRow` README (a "Notifications row" table) and the values in the `SettingsIndex` README beside "Not saved" and "Check focus minutes". The *Ask macOS* action is a quiet `Button`, the control the denied rows already use, so no new component is needed.

  The denied lines are plain `ink` text with no glyph, never amber or critical (design-system rule 29). If *Open System Settings* fails, the line adds "Find Orasenda in System Settings, Notifications." and the failure is logged.
- **The end notification** still needs both: spec A's rule (completed end, `notify.session_end` true, status `granted`, re-read before posting, `scheduler.rs:189-201`) is unchanged.
- **Permission answered in System Settings** while Orasenda is in the background: the focus re-read updates the status. The box doesn't change, because the preference is the user's. A `denied`+on row turns into `granted`+on.
- **The review on a pre-B database:** stored `true` or absent with `granted` → stays on. `true` or absent with `notDetermined` or `denied` → off, so no prompt ever comes. `false` → stays off. `unavailable` → pending until a bundled launch. A save that changes the preference before the review (a tick or untick) removes the marker, so the user's value stands. Any other save (theme, preset, minutes) echoes the presented value, leaves `notify.session_end` and the marker alone, and logs no `change_log` row for it.
- **Before the launch status read arrives** (milliseconds after launch, normally before anyone opens Settings): the view's status is `unavailable` until then (spec A), so the Notifications row shows its disabled `unavailable` state, and while a review is pending the presented preference is `false`. When the read lands, the review runs and `settings-changed` and `timer-tick` bring the real row. A granted A-era user may see the box go from off and disabled to on and enabled once, if they reach Settings within that moment (⌘, at a cold start). That is accepted: the box can't be ticked while disabled, so no save races the review, and no "review pending" state is added.
- **Fresh install:** no marker; `notify.session_end` absent reads `false`; the first *Start focus* asks nothing.
- **Theme while a session runs** applies at once. Nothing about the timer changes. **Theme save fails:** the radios roll back, nothing was applied in Rust, and the webview's `data-theme` never moved (it follows Rust's `settings-changed`, not the optimistic radio).
- **Two editors of the Custom minutes until C.** Today keeps its preset radios and Custom fields until C removes them, so the same two settings have two editors, but only one page is mounted at a time and both save through the one chain. Today's handling stays exactly as it is: its `invalidSpec` helper (`rangeHelpFor`, `Today.tsx:73-78`) and its silent rollback on `write` (spec A line 239, amended below). `customRange.ts` moves the bounds and helper strings out of Today without changing what Today shows, and Today's existing tests are the check. The #120 Today half (the refused start's "Open Settings") is C's; B does nothing to it beyond providing the field targets.
- **Custom field rules:** saved on blur or Return, never per keystroke. Esc puts back the saved value and clears that field's error. A value that is not a whole number (empty, "4.5", "abc": `type="number"` gives `""` for the last) is refused locally with the field's range line and isn't sent. An in-range value is sent, and Rust's `invalidSpec` maps to the field by the shared `customRange.ts` bounds, as `rangeHelpFor` does today (`Today.tsx:73-78`). Typing in a Custom field never changes the preset. A Custom value saved while *Classic* is chosen is kept for when Custom is chosen.
- **Store unavailable at launch** (the read failed and the scheduler retries every second, spec A line 240): the controls show the defaults and stay usable. The standing line is true for both causes ("may not be kept"). When the read recovers, `settings-changed` reloads the page with the stored values. If the store never opened, every save fails with `unavailable`, rolls back and says so.
- **Store newer:** read-only. Theme follows the defaults (`system`).
- **Navigation while a save is in flight:** the chain outlives the page (`settingsQueue.ts:12-14`), so the save still completes, and its failure copy shows on the next visit only if the page is open. Leaving the page resets the save line.
- **⌘, with the window closed or hidden, or at a cold start:** `show_settings` stores the pending page, shows, unminimizes and focuses `main` (`show_main`, `lifecycle.rs:56-70`), then emits `navigate`. A webview that wasn't listening yet takes the pending page when its listener is registered, so it opens on Settings. Closing `main` only hides it, so its webview and listener survive.
- **⌘, or *Settings…* while a session runs, with `main` on another Space or in full screen:** the same `show_settings`. `set_focus` activates the app, and macOS moves to `main`'s Space. The session is untouched. Orasenda never changes its activation policy (it is a regular app with a Dock icon; nothing in `src-tauri/src` sets one), so nothing needs switching.
- **Reduce motion:** theme switches with no cross-fade (design system, "Theme switches at once"). Nothing animates.
- **StrictMode double mount:** `useTheme`, `navigate` and `settings-changed` use the shell's `subscribe()` (`apps/orasenda/src/subscribe.ts:16-47`), so one listener remains.
- **Quit and relaunch** keep wall-clock time exactly as spec A says (owner decision, unchanged): a running session resumes with its true remaining time. Nothing in B touches it.

## FAQ
### Why a separate `notifications_request` command rather than asking from `settings_set`?
A save is fast and chained. A permission prompt can stay open for minutes. Putting the prompt inside `settings_set` would hold the save chain for as long as the prompt is up, and would make a preference write depend on an OS answer. The command asks and reports. The webview then saves the preference through the same chain as every other setting, so "Newest wins" holds and an untick while asking is simple.

### Why does a ticked box stay ticked when macOS denies it later?
The preference is the user's and the status is macOS's. Keeping both visible ("On here, but macOS has notifications off…") tells the user exactly what to change and where. Clearing the box would change a setting behind the user's back. The first *Don't Allow* is different: it answers the tick that asked, so the box goes back off.

### Why a store migration for the notify review rather than a check at every launch?
The review needs to know whether the database predates B. Only a migration can tell, from inside the database, without the store API reporting the version it found. Migration 0002 writes the marker only when `device_id` already exists, which is true only for a file A created. The marker is device-only because the permission it is checked against is per device.

### Why both `set_theme` and `data-theme`?
`AppHandle::set_theme` sets `NSApplication.appearance`, which drives the title bar, the menu-bar menu and WKWebView's `prefers-color-scheme`, so on macOS it alone would be enough. `data-theme` keeps the CSS honest where the OS doesn't propagate the choice (jsdom tests, C's Playwright harness, Windows' WebView2) and gives later windows one documented switch. The tokens build emits both selectors from the same values, so nothing is duplicated by hand.

### Why doesn't B build the Playwright layout harness?
The ruling puts it in C's first task, where its first failing measurement is #119 on Today. The design review said the harness "gates the first code change", meaning the first change that relies on "pages never scroll; regions do" at the new sizes. B doesn't change the window minimum and ships only the regular layout. B checks its layout in WKWebView by hand, and C's harness adds the Settings cases before C makes Settings compact.

### Why is the theme a syncable setting?
Spec A's settings are syncable and nothing in P1 syncs, so the choice costs nothing now. Whether theme should differ per Mac is an owner question below. Changing it later means moving one key to device-only storage.

## Open questions
These are owner calls. Each has a recommendation, and the spec is written to it.

1. **About: Orasenda's licence line only, or also an "Open-source licences" list?** Recommendation: the line only in B, and the list as its own backlog item. The third-party notices are not a nicety: shipping binaries that include MIT and Apache-2.0 dependencies obliges Orasenda to carry their licence notices. So the backlog item is a **hard precondition for the first build shared outside the owner's machine** (any private beta included), not an "ideally". It needs a generator (a new build step or tool, vetted with baton:deps) and a page for it, which is why it isn't in B.
2. **Should the theme follow you across Macs (syncable, as written) or stay per Mac (device-only)?** Recommendation: syncable for now, as the ruling says ("stored as a setting"), and revisit with P10 sync.
