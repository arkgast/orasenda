## Overview
One design-system task, then six code tasks, in four waves. The spec's Decisions section asks
for one design-system task and five code tasks: (1) store migration and settings diff,
(2) notifications and the notify review, (3) menus, navigation and theme application with the
tokens build, (4) the Settings page, (5) closing. Planning keeps that cut and adds one task in
front of it, because the spec's tasks 1 to 3 all edit the same eight files (`ipc.rs`,
`session.rs`, `scheduler.rs`, `lib.rs`, `commands.rs`, `commands.list.rs`,
`capabilities/main.json` and the generated `bindings.ts`), and the Settings page needs the IPC
contract before any of them finishes. "Shared foundations become their own task": the new
**T2** lays the whole IPC contract once, with interim bodies, and every later task builds on it
without editing those files again.

| Plan task | Spec task | What |
|---|---|---|
| **T1** | design-system task | The seven components in the artifact's `bundle.js`, the README additions, `design/system/` refreshed, `packages/ui` regenerated and tested |
| **T2** | (new: the shared contract) | `Settings` (was `TimerSettings`) with `Theme`, the three commands, the two events, `PendingNavigate`, the `notifications.rs` skeleton, `bindings.ts` |
| **T3** | (1) | Migration `0002` and `meta.rs`; the settings diff, presented settings, the notify review; `settings-changed` and the theme after a save; `timer_start` stops asking |
| **T4** | (2) | `notifications_request` with one prompt for every waiter, `notifications_open_settings`, the focus re-read, the review from every status trigger; `Notifier::open_settings` |
| **T5** | (3) | The app menu with ⌘,, *Settings…* in the menu-bar menu, `show_settings`, the window shown after `set_theme`, the tokens build |
| **T6** | (4) | The Settings page, `settingsQueue.ts`, `notificationsToggle.ts`, `useTheme.ts`, `customRange.ts`, Today's explanation line removed |
| **T7** | (5) | ADR-014 accepted, the spec and plan status, the owner's manual acceptance recorded |

- **Wave 1** (now, in parallel): **T1** and **T2**. T1 is design-first: the orchestrator updates
  the live artifact before the PR (see T1). T2 is mechanical.
- **Wave 2**: **T3** as soon as T2 merges. **T6** as soon as T1 and T2 have both merged; it
  touches only `apps/orasenda/src/**`, so it runs beside T3, T4 and T5.
- **Wave 3** (after T3): **T4** and **T5** in parallel.
- **Wave 4** (after T4, T5 and T6): **T7**.

The app crate is cut along the files, not the features: T3 owns `session.rs` and the store,
T4 owns `scheduler.rs` and `notifications.rs`, T5 owns `lifecycle.rs`, `lib.rs`, `tray.rs` and
the new `app_menu.rs`. Each later task's edits of another task's file are listed in its
Touches and happen only while that file's owner is not running (see
[File ownership](#file-ownership-who-edits-each-shared-file-and-when)).

**Conventions for every task** (from `docs/conventions.md`, `docs/common-issues.md`, plan A):
IPC structs and enums use `#[serde(rename_all = "camelCase")]` and enum variants are spelled as
the spec spells them (`Theme` and `NavigatePage` lowercase); `bindings.ts` is generated by
`just bindings` and never edited by hand, and a rebase regenerates it rather than merging it;
every new command goes into `commands.list.rs`, `specta_builder()` and
`capabilities/main.json`, with its generated `permissions/autogenerated/<command>.toml`
committed; no lock is held across an AppKit, tray, menu, window or `set_theme` call, and
`settings-changed` is never emitted under the session lock; an unknown value from the OS, the
store or IPC maps to the failure side; replies that can overlap are chained or numbered
("Newest wins"); every `unsafe` block has a `// SAFETY:` comment; desktop-only Tauri APIs
(`tauri::menu`, the tray, and any other the mobile check rejects) are behind
`#[cfg(desktop)]`, since `just mobile` checks the app crate for iOS and Android; the
**`windows (advisory)` job is green on `main`** since #78, so a red Windows job is a real
regression to fix in the task, not a baseline. Green CI means `gh pr checks <pr> --required`
passes and the Windows job is green; agents check it once and never with `--watch`. Each task
is one squash-merged PR. **mechanical** tasks have a fixed shape and a complete contract;
**cross-file/debugging** tasks need judgement across modules or the running app.

## Contract
- **IPC contract (T2):** `Theme`, `Settings` (replacing `TimerSettings`), `NavigatePage`, the
  events `settings-changed` (`SettingsChanged`) and `navigate` (`Navigate`),
  `NotificationsError`/`NotificationsErrorKind`, the commands `notifications_request`,
  `notifications_open_settings` and `navigate_take`, their manifest, capability and permission
  entries, and the regenerated `bindings.ts`. T3, T4 and T5 fill in behaviour **without
  changing `bindings.ts`** (each has that as acceptance); T6 builds against it with `mockIPC`.
- **App-crate seams (T2):** `notifications.rs` with the three entry points the commands and
  the focus handler call (interim bodies, replaced by T4), `lifecycle::PendingNavigate` (final),
  and the `Focused(true)` hook that calls `notifications::on_main_focused`.
- **Host seams (T3):** `Host::emit_settings_changed`, `Host::apply_theme`,
  `scheduler::tauri_theme`, `SessionService::run_notify_review`. T4 and T5 consume them and
  don't change their signatures.
- **Design-system contract (T1):** the seven components exported from `@orasenda/ui` with the
  props in `packages/ui/components.d.ts` (the `*NextProps` of `Input`, `InlineNotice` and
  `EmptyState` folded into their `Props`), and the README rows the page's copy comes from.

## Impact
Risky changes: a schema migration, a settings default flipped on existing data, a public IPC
type renamed, the main window shown later at launch, the app menu replaced, the tokens'
dark-mode selector changed.
- **Affected call paths / consumers:**
  - `TimerSettings` → `Settings` (T2): `commands.rs` (`settings_get`, `settings_set`),
    `session.rs` (`read_settings`, `set_settings`, `settings`, `current_settings`,
    `run_set_settings`, the tests), `ipc.rs` tests, and in TypeScript `settingsQueue.ts`
    (`SETTINGS_KEYS` gains `"theme"`; its compile-time check fails until it does),
    `settingsQueue.test.ts`, `ui-types.test-d.tsx`, `pages/Today.tsx`, `pages/Today.test.tsx`,
    `pages/testing.ts`. Today keeps working: it saves `{ ...latest(), preset }`, so the theme
    travels along unchanged.
  - `timer_start` stops asking (T3): `Outcome.request_notifications`,
    `Effects.request_notifications`, the `matches!` in `start` and the call in
    `scheduler::publish` go; between T3 and T4 nothing asks for the permission at all (dev
    builds only; nothing ships before T7).
  - `scheduler::store_status` runs the pending review (T4), so every status read (launch,
    focus, request answer, the re-read before posting at a completed end) can write one setting.
  - Launch order (T5): `main` starts hidden (`tauri.conf.json`), `setup()` ends with
    `apply_theme` then `show_main`. An error earlier in `setup()` already aborts the launch, so
    no path leaves a running app with no window.
  - App menu (T5): `Builder::menu(app_menu::build)` replaces Tauri's implicit default; it starts
    from `Menu::default(app)`, so Edit (copy, paste, undo in text fields), Window and Hide keep
    working.
  - Tokens (T5): the dark block moves under `:root:not([data-theme="light"])` inside the media
    query and is repeated under `:root[data-theme="dark"]`. The spike overlay window sets no
    `data-theme`, so it still follows the system.
- **Data and migrations (expand → migrate → contract):**
  - Expand: `0002_notify_review.sql` adds a device-only `meta` row `notify_review = pending` only
    on a file whose `meta.device_id` already exists (a file A created); `user_version` 1 → 2;
    `SCHEMA_VERSION = 2`. New key `ui.theme`: absent reads `system`, no backfill.
  - Migrate: the first status read that knows the answer (`granted`, `denied`,
    `notDetermined`) runs the review once: `notify.session_end = (stored, or true when absent)
    && status == granted`, plus `meta::remove("notify_review")`, in one transaction.
    `unavailable` (unbundled `tauri dev`) leaves it pending. A user's tick or untick before the
    review removes the marker and wins.
  - Contract: the `notify.session_end` default becomes `false`. Nothing else is removed.
- **Tests and downstream checks that must stay green:** `newer_user_version_is_refused_and_untouched`
  (`SCHEMA_VERSION + 1`), every store test that asserts the schema version, Today's Custom-field
  and `invalidSpec` tests after the move to `customRange.ts`, `App.test.tsx` (StrictMode and
  subscription counts), `settingsQueue.test.ts` (held promises, "Newest wins"),
  `manifest_commands_match_specta_builder`, the capability tests, `export_bindings` and the
  `bindings.ts` staleness check on macOS and Windows, `styles.test.ts` (token-only CSS), the
  tokens and `packages/ui` build checks in `ci.sh`, `just mobile`.
- **Rollout and rollback:** each task is one squash-merged PR; revert it to roll back. The
  migration is forward-only: reverting T3 leaves v2 files that an A-era build refuses as newer
  (`store: newer`, read-only). That affects only a developer switching branches and is accepted
  by the spec ("Data & migrations"); never revert T3 on a machine whose data matters without
  restoring the file. T1 is rolled back by republishing the previous artifact version and
  refreshing `design/system/`.
